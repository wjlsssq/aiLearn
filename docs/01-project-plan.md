# 项目与学习计划

制定日期：2026-11-05。学习者画像：有 Java / 后端经验，Python 较少，LangChain 从基础开始。

## 1. 学习目标和业务场景

项目名称：**ShopMind 智能售后客服**。

业务闭环：店铺规则问答 → 多轮追问 → 订单查询 → 售后草稿 → 用户确认 → 创建模拟工单 → 查看执行与评估结果。

选这个场景的原因：业务容易理解，非结构化规则与结构化订单同时存在；能用真实功能解释 RAG、工具调用、记忆、工作流、持久化和事务；每个阶段都有可见页面和可复现的成功、失败案例。

完成后应能做到：

1. 独立运行前端、后端和 MySQL，说明一条请求如何经过各层。
2. 解释模型调用、Prompt、Runnable、结构化输出和流式响应。
3. 自己搭建并评估文档入库、Embedding、检索、重排和引用回答流程。
4. 区分固定流程、Agent 决策、工具执行和服务端权限控制。
5. 演示用户确认、重启恢复、幂等写入和跨用户隔离。
6. 用项目中的实际数据和失败案例回答面试追问。

模型通过后端环境配置选择，分别配置聊天模型和 Embedding 模型。阶段 0 核对用户可用的服务、访问方式、流式输出、结构化输出和工具调用能力；不假设所有兼容接口都完整支持这些能力。真实调用需要用户自己的凭据；凭据不放前端，也不写进版本库。无凭据时先完成模拟响应的接口联调，模拟结果与真实模型结果明确标注。

### MySQL 与向量检索的边界

核心路线只要求一个数据库服务：MySQL。向量数组保存在 MySQL 的 JSON 字段，后端在筛选出允许访问的有效分块后计算余弦相似度。初始语料控制在约 1,000 个分块，规模以实测延迟与内存为准。

JSON 保存向量不会自动获得向量索引，也不等于数据库内的近邻检索。应用内精确扫描作为教学基线；后续通过性能实验讨论 ANN，并可选用 FAISS 作为可从 MySQL 重建的派生索引。Milvus、Redis、PostgreSQL 均不是主线必需依赖。

MySQL 的中文关键词召回使用 ngram 全文解析器，教学时检查分词粒度、停用词及短词表现，不能直接把默认英文分词配置当作中文检索方案。[依据：MySQL ngram 文档](https://dev.mysql.com/doc/refman/8.4/en/fulltext-search-ngram.html)。

## 3. 目标架构

```text
Vue 页面
  ├─ 聊天与引用卡片
  ├─ 知识库与检索实验
  ├─ 订单与售后确认
  └─ 执行记录与评估面板
         │ HTTP / 流式事件
         ▼
FastAPI 路由 → Service → Repository → MySQL
                   │
                   ├─ Prompt / Runnable / 模型适配
                   ├─ 文档切分 / Embedding / Retriever / Reranker
                   ├─ LangChain Agent / 白名单业务工具
                   └─ LangGraph / MySQL checkpoint 适配
```

LangChain 封装模型与工具，LangGraph 用于需要明确状态和流程控制的模块。普通订单查询仍调用确定性的业务服务，由服务端检查订单归属；模型输出工具名和参数，实际执行发生在后端。

前端每次新增功能只增加必要页面元素，重点保留能帮助解释概念的观察面板：最终发送的消息、检索候选、引用来源、工具输入输出、节点状态、耗时与 Token 用量。界面展示可观测的执行信息，不把模型内部推理文本作为展示要求。

目标目录（后续逐步创建）：

```text
frontend/src/
  api/                 # 后端调用与流式事件读取
  views/               # chat、knowledge、orders、after-sales、evaluation
  components/          # 消息、引用、工具状态、确认卡片
backend/
  app/api/             # HTTP 路由，类似 Spring Controller
  app/schemas/         # Pydantic DTO 与入参、出参校验
  app/services/        # 业务编排与事务边界
  app/repositories/    # 数据访问，类似 DAO / Mapper
  app/models/          # SQLAlchemy 实体与表映射
  app/ai/              # models、prompts、chains、rag、tools、graphs
  app/core/            # 配置、日志、依赖注入与异常映射
  migrations/          # Alembic 数据库迁移
  tests/               # 隔离、幂等、恢复与核心流程测试
datasets/              # 合成店铺规则、订单样本、评估集
docs/lessons/          # 每题一份课程与代码阅读指南
```

## 6. MySQL 数据设计草案

表按阶段逐步创建，当前不预建全部表。

| 表 | 用途 | 重要约束或索引 |
| --- | --- | --- |
| `users` | 教学用户与角色 | 用户名唯一；密码仅保存哈希 |
| `products` | 模拟商品 | SKU 唯一 |
| `orders` / `order_items` | 模拟订单与明细 | 订单号唯一；订单归属用户索引；金额用 DECIMAL |
| `knowledge_documents` | 文档、版本、哈希、有效状态与访问范围 | 文档哈希与版本用于重复导入、更新和撤销 |
| `knowledge_chunks` | 分块正文、位置、来源和元信息 | 文档版本 + 分块序号；中文 FULLTEXT 索引 |
| `chunk_embeddings` | 向量 JSON、模型标识、维度、版本 | 分块 + Embedding 版本唯一；查询与文档向量使用同一空间 |
| `chat_sessions` | 会话归属、标题、上下文摘要 | 用户 + 更新时间索引 |
| `chat_messages` | 消息、角色、工具关联和状态 | 会话 + 序号唯一；区分生成中、完成、失败 |
| `after_sales_drafts` | 模型提出的售后草稿、待确认状态和内容版本 | 用户归属；确认时重查订单状态与草稿版本 |
| `after_sales_requests` | 用户确认后的模拟工单 | 用户 + 幂等键唯一；事务校验与状态转移 |
| `operation_logs` | 写操作、确认、拒绝和操作结果 | 用户、业务对象、时间、请求关联 |
| `agent_runs` / `agent_steps` | 模型、检索、工具、图节点的执行记录 | trace_id / run_id、状态、耗时和用量 |
| `evaluation_cases` / `evaluation_results` | 问题、证据标签、预期工具与实测结果 | 数据集版本、配置版本与运行关联 |

LangGraph checkpoint 的表由最终采用的 saver 创建和维护，与业务表分开管理，不手写一个普通 JSON 状态表就声称实现完整 checkpoint。

### LangGraph 的 MySQL 持久化

官方文档区分 thread checkpoint 与跨 thread 的长期数据。聊天记录表、业务草稿表与图 checkpoint 各有职责，不能互相替代。[依据：官方持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)。

Q15 先验证社区 `langgraph-checkpoint-mysql` 与锁定 LangGraph / MySQL 版本的兼容性，覆盖多轮状态、并发隔离、interrupt/resume 和进程重启。它是社区实现，不能描述为官方内置能力。[实现来源](https://github.com/tjni/langgraph-checkpoint-mysql)。

若社区实现无法通过必要场景，将在本模块修正适配或实现所需的 saver 接口；该工作可能增加课时。完整恢复验收通过前，不把内存 saver 或业务表重放标为持久化功能完成。开发早期可以使用内存状态演示流程，但必须标清重启会丢失图状态。

## 7. 每一课的固定交付

1. **面试题**：给出主问题和场景，让学习者先试答。
2. **功能演示**：先说明本课结束后用户可以做什么。
3. **最小知识**：用 Java 概念对照 Python；介绍本题需要的 AI 概念。
4. **请求链路**：从 Vue 事件逐步走到路由、服务、AI 组件、数据库和返回结果。
5. **逐行代码**：提供完整可运行的小步改动和中文注释，不使用省略号代替关键实现。
6. **对照实验**：只改变一个关键变量，观察实际差异。
7. **验收案例**：正常、边界和失败场景；需要时添加有意义的自动化测试。
8. **面试表达**：形成 30 秒结论、2 分钟项目回答和进阶追问。
9. **动手练习**：让学习者修改一个行为并解释原因；记录不会的概念和下次复习点。

### 逐行注释约定

- 手写教学代码按行添加中文注释，覆盖 Python、TypeScript、Vue 逻辑和 SQL。
- 每条有含义的语句解释“做什么”；关键语句还解释“为什么”和“输入输出是什么”。
- 多行调用、条件与数据结构在相邻行写注释；使用该语言合法的注释方式，确保代码可运行。
- 函数文档写清参数、返回值、业务边界和异常；工具函数额外写清用途与参数约束。
- SQL 表与字段写 COMMENT，迁移说明索引、唯一约束与事务考虑。
- 空行、纯闭合符号和自动生成文件不添加机械注释；对应语法由课程讲义解释。
- 讲义使用当前文件的实际行号或代码片段定位，随着代码改动同步更新。
- 新出现的框架语法先解释一次，避免用“框架自动处理”跳过核心流程。

## 8. 贯穿项目的验证方式

种子数据先准备两个普通用户、一个知识库管理员、约 20 笔不同状态订单，以及商品说明、退换货、发票和配送等合成规则。Markdown / TXT 先行；PDF 解析在文本流程稳定后增加，扫描件 OCR 作为扩展。

固定评估集由项目自己整理并标注，初始目标 50 题：规则问答 20、跨轮指代 5、工具查询与流程 10、证据不足 5、越权或恶意指令 10。用其中 30 题调整参数，保留 20 题做最终验证；同一验证集不反复用于调参。

- 切分与检索：记录命中证据、Recall@K、MRR 和分块参数。
- 回答：区分正确性、证据支持、引用一致性和合理拒答；人工复核一部分结果。
- 工具与流程：记录选对工具、参数正确、实际任务完成、确认和幂等情况。
- 性能：分别记录首个文本事件延迟、端到端延迟、模型/工具耗时、Token 与费用估算。
- 外部模型故障使用可控模拟重现；真实模型冒烟测试单独记录供应商、模型与时间。
- 指标均以实际运行结果为准；没有运行数据时不写“准确率 95%”等结论。
