# 代码架构与开发规范

以根目录 AGENTS.md 为约束。业务界面服务实际工作流，中文注释与独立文档解释实现；不把教学实验、技术参数、假统计塞进产品页面。

## 前端结构

- `App.vue`：中文组件配置与页面入口。`main.ts` 只注册实际使用的 Element Plus 组件。
- `views/WorkbenchView.vue`：业务导航和会话布局；桌面会话页由左侧导航、会话列表与消息区组成，不再设置顶部面包屑/连接状态栏和右侧固定订单栏。手机保留独立的导航入口，订单/资料快捷操作只预填聊天需求。`OrdersView.vue` / `KnowledgeView.vue` 组合订单与资料管理页面。
- `components/workbench`：登录、会话列表和消息区；`components/agent/ChatResult.vue`：消息内的查询表格与资料卡片；`components/common`：一致的图标。已移除独立订单助手、资料整理抽屉和固定订单快捷栏。
- `composables`：useWorkbench 负责流式、工具进度、业务结果、取消和重试；useKnowledge 管理规则文档。身份变化后的旧响应仍需拒收。
- `api/client.ts`：认证头、错误转换、204 和流读取。按业务域的 API 文件不访问组件状态。
- `types`：请求响应契约；`utils`：凭据存储和纯 SSE 解析。
- `styles`：theme / app-shell / conversations / resources / login 各司其职，workbench.css 聚合并放响应式规则。

组件通过 props/emits 协作，不直接发 HTTP。所有手写 Vue/TS/CSS/JSON 运行项目 Prettier；修改后执行 format:check 和 build。依赖通过 scripts/install_frontend.ps1 安装到 E 盘，不在源码目录 npm install。

## 后端结构

API 只适配 HTTP，Service 决定身份、业务规则与事务，Repository 写参数化 SQL，ORM/DB 定义实体和连接。业务异常在 main.py 统一映射为 HTTP；不得反向导入应用入口获得配置。

- `api/routes/auth.py`：login / me / logout；退出只撤销当前令牌。
- `services/chat.py` 管理会话归属、历史和正文/卡片成对写入；真实模式交给 services/agent_chat.py 绑定身份与工具业务回调，数据库事务不跨模型等待。
- `ai/agents/customer_service.py` 使用 create_agent 管理真实工具循环和预算；`ai/tools/customer_service.py` 只包装回调与输入协议，不反向导入业务层。
- 模型上下文由后端根据已验证的会话归属加载授权历史，再结合当前工具结果构造；历史结果通过 `ai/prompts/history.py` 按预算摘要。原右侧“业务上下文”只是当前账号前几笔订单的固定快捷列表，既不是模型输入，也不代表 Agent 已查询或正在处理的订单。界面以对应消息内的结果展示本轮实际查询。
- `core/order_query.py` 校验 SQL 语法子集、绑定常量并注入当前用户的派生表范围；`services/agent_query.py` 负责校验/查询/审计规则；`repositories/agent.py` 执行实际只读查询与审计持久化；`db/agent_query.py` 不回退业务账号。
- `api/routes/assistant.py`、`services/assistant.py` 和原单订单工具保留旧接口兼容，当前页面不再调用；新能力只接统一聊天，不在旧流程重复实现。
- `services/draft.py` 保留字段与来源检查，草稿不等于工单；服务未启用时不返回固定演示结果。
- `services/knowledge.py` 管理私有文档与版本，切分由 ai/rag/splitter.py 内部完成；接口不再提供教学样例或分块 A/B 预览。
- 新表与改表经 `backend/migrations` / `backend/alembic.ini` 管理，原五张表仅保留初始化基线。
- `scripts/setup_agent_database.py` 只配置本地查询账号和 .env；模型无此权限。新电脑必须先升级到 0004_order_exports，再配置独立只读连接。
- `scripts/seed_business_data.py` 只用于本地开发样本追加，默认预览；批量用户和订单在同一事务写入，不作为 HTTP 产品接口，运行数据和凭据仅存忽略目录。用法见 [业务数据](10-本地业务样本数据.md)。
- `database/snapshots` 存放用户明确授权提交的开发库全量 SQL，`database/README.md` 说明恢复和验证；`scripts/export_database.py` 调用原生 mysqldump 更新快照，不自动导入或覆盖现有库。其他运行数据和明文凭据仍不提交。

## 验证与交接

必须验证真实 MySQL、认证和数据归属；模型测试使用内存 HTTP 传输验证真实适配器，不消耗付费额度。SSE 测试检查中文跨字节、合并帧和截断。UI 验收在独立端口运行，临时替身与日志不提交，原有服务不被重启。

修改前 git status → git pull --ff-only → 读 AGENTS.md / 交接；完成后更新交接、检查暂存区、提交并推送。环境、密钥、IDE、依赖、缓存和运行产物不得提交。用户原有未提交笔记保留。

## 订单业务数据

订单模型保存一单一商品规格的金额、生命周期、收货和物流快照；Service 通过明确 DTO 输出，金额保持十进制字符串。0003_order_details 增量迁移与用户/下单时间索引由 Alembic 管理。scripts/business_order_details.py 负责合成规则，seed_business_data.py 用于新增，enrich_business_orders.py 仅补齐旧合成数据，不覆盖人工值。字段与金额口径见 [业务样本数据](10-本地业务样本数据.md)。

## 订单导出

Excel 导出通过同一聊天 Agent 的 export_orders_excel 工具调度，独立日期筛选读取不复用 50 行聊天结果。schemas/order_export.py 校验条件，services/order_export.py 负责规则与文件生成，repositories/order_export.py 负责只读视图查询及快照持久化，api/routes/order_export.py 适配认证下载。前端 API、useOrderExport 和 ChatResult 分别承担传输、操作状态和卡片；只把文件摘要放回模型。规则见 [订单 Excel 导出](11-订单Excel导出.md)。
