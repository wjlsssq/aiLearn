# Q13：智能体如何在聊天中选择工具并完成业务查询？

更新：2026-11-17。本阶段把实际订单查询与售后资料整理统一到聊天。页面只显示业务进度、答复和结果，不展示 SQL、工具协议或教学过程。

## 业务验收

重新启动 IDEA 中的 backend/run.py，刷新前端后可以直接发送：

- “按状态统计我的订单数量。”
- “统计我 2026 年 10 月的实付金额和退款金额。”
- “查询 DEMO-A001 的收货地址、实付金额和下单时间。”
- “查找耳机相关、正在售后的订单。”
- “查询订单 DEMO-A001 的当前状态。”
- “我的 DEMO-A001 耳机损坏了，想退货，数量1，请整理售后资料。”

订单中心的查询操作会把问题带回聊天输入框，用户可编辑后发送。查询结果以表格展示，资料以卡片展示；完整回复成功后，它们与问答一起保存，刷新后重新打开会话可恢复。资料卡片不代表已建单、退款或通过售后资格检查。会话页不再显示固定订单侧栏，模型使用的上下文由后端按当前账号和会话加载，与页面订单列表无关。

## 一轮消息的数据流

```text
聊天界面 → /api/chat/stream → services/chat.py
  认证与会话归属 → 读取授权历史 → 释放只读事务
  → services/agent_chat.py 绑定身份与用户原文
  → ai/agents/customer_service.py 的 create_agent
     → 模型自行选择查询工具、资料工具，或直接回答
     → 工具结果返回模型，模型可在预算内调整查询
  → 最终正文与业务卡片成对提交 MySQL → done 确认保存
```

同步 /api/chat 复用相同 Agent；mock 仅保留既有自动化回归路径。原 /api/assistant/orders、/api/drafts/extract 暂保留兼容，不再有独立前端入口。Agent 查询不经过旧单订单助手的固定两次模型流程。

流协议保留 start/delta/done/error，新增 activity、artifact、answer_reset。工具进度为固定中文标签；模型在查工具之前的过渡文字会重置，数据库只保存最终答复。业务卡片和答复在同一事务保存；失败、输出截断、缺少正常结束或取消时不保存半轮。已经发生的只读查询及其审计不会因为用户取消而撤销。

## 查询权限怎样落实

模型可以生成 SQL，入口是 query_my_orders(sql)，提供逻辑表 my_orders 的编号、商品、状态及金额、时间、收货物流业务白名单字段。当前支持单表 SELECT、筛选、LIKE、IN、排序、分组、HAVING、COUNT/SUM/AVG/MIN/MAX 和分页；不支持联表、子查询、公共表表达式、任意函数或写操作。这是当前受控查询子集，不是整库通用 SQL 控制台。

执行器依次完成：

1. SQLGlot 按 MySQL 方言解析，限定一条查询、允许的语法树节点、表、列和函数；解析成功本身不等于安全或语义正确。
2. 将 my_orders 替换为只含公开列的派生查询，内部绑定 `WHERE user_id = :actor_id`。模型的 WHERE、OR 条件和聚合都作用于已限定的数据，不是最后简单拼接一个 WHERE。
3. 模型提供的字符串与数值全部转成绑定参数；身份来自认证闭包，模型不能传入或覆盖。
4. 使用独立账号 SELECT agent_order_data；该账号不能读 users、access_tokens、基础 orders 表，也不能更新视图。
5. 最多 50 行、8 列，分页偏移最多 2000。额外取一条判断是否截断；查询超时默认 2000 毫秒，结果大小也有限制。总量统计必须执行 COUNT，不能从前 50 行推断。
6. 查询前写入 pending 审计，结束后记录成功、拒绝或失败、行数、耗时和安全错误码。审计不可用时不向模型交付查询结果，不回显数据库原始异常或凭据。

只读权限和当前用户隔离分别由数据库授权、后端编译器落实。共享数据库连接身份不能直接代替应用用户身份。对用户请求的金额、时间、真实物流分析，当前表没有这些字段，助手应说明缺少数据。

## 资料来源与执行预算

prepare_after_sales 无参数，后端从授权历史中的用户消息与当前消息取最近 2000 字原文。模型不能自己编造一段 description 再当作用户原话。结构化提取继续使用严格 Pydantic 校验及订单号来源检查；资料本身不证明订单归属或售后资格。

Agent 每轮最多 4 次主模型调用、3 次实际工具执行，单次模型最多提出 2 个工具；资料提取每轮最多 1 次额外模型调用。最坏合计 5 次模型请求，不隐藏自动网络重试。重复标识、未知工具、无效调用和超预算会终止处理，失败不写入成功问答。

资料提取的嵌套模型显式禁用框架自动流式，先取得完整 JSON 再校验；只有主模型的用户答复增量进入聊天。历史结果以有限行摘要参与后续上下文，并标注需要重新查询实时状态。

## 面试表达与当前边界

“固定调用链由代码预先决定步骤；本项目的 Agent 根据消息和工具结果选择下一步，能自行查询、纠正受拒 SQL 或追问。模型负责提出动作，服务端负责权限、参数、预算和执行。SQL 查询采用逻辑表白名单、强制用户范围、参数绑定和独立只读授权；写业务仍需专用服务、确认和幂等。”

create_agent 底层使用图执行，但本次执行状态仅在请求内；MySQL 保存业务会话与卡片，不等于已经接入图检查点。显式售后流程、重启恢复、审批和写操作幂等留待后续阶段。并发同会话仍读取各自开始时的历史快照，没有新增跨设备串行化。

验证使用真实本地 MySQL、两种真实供应商适配器的内存 HTTP 响应和独立端口浏览器，未消耗真实模型额度；不能把这些结果描述成 DeepSeek 实际选工具效果已验收。
